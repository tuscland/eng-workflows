# Deliver Parent

```text
/deliver-parent <parent-issue-or-local-run>
```

This skill coordinates `$issue-tree-audit`, `$implement-ticket`, and `$finalize-parent`; those skills retain ownership of repository reconciliation, implementation, review, publication, cleanup, end-to-end evidence, and final reporting. Read all three skills and their routed references before acting. This workflow explicitly authorizes the delivery skills' review subagents.

Invocation authorizes marking each cleared child pull request ready and merging it into the declared integration branch after the gates below pass. It never authorizes merging the integration pull request into its target. Never merge a pull request whose base is `main`, the repository's default branch, or any branch other than the exact declared integration branch. Never push implementation directly to `main`.

## Workflow

1. **Audit freshness before delivery work.** Perform only the minimum read-only discovery needed to identify the canonical parent repository, its current default and declared target branches, and the parent issue tree. Fetch their current remote tips, record the working-tree status, then run `$issue-tree-audit` in read-only mode over the full parent and ticket tree. Compare the specification, acceptance criteria, ticket boundaries, blocker graph, named paths and APIs, implementation assumptions, and test expectations with current code, tests, documentation, schemas, and merged history. Inspect changes since the planning baseline, including work newly landed on `main` or the declared target, for already-delivered outcomes, conflicts, duplication, changed dependencies, or invalidated assumptions. Do not create a branch or worktree, change project status, edit the tracker, or start implementation during this gate.
2. **Decide whether the plan is still executable.** Record an evidence-backed result for every ticket. Proceed only when the parent outcome and every required ticket remain correct, complete, nonduplicative, and implementable against current repository state. Harmless code movement may be reconciled only when it leaves the stated behavior, acceptance criteria, boundaries, ordering, and architecture decisions intact; record the updated factual reference. Any drift that changes scope, behavior, acceptance criteria, ticket decomposition, dependencies, or an architectural choice blocks delivery and returns the audit findings for specification or ticket revision. A capability already delivered on the target is not implemented again. Never silently reinterpret a stale ticket or use implementation to resolve a product decision.
3. **Resolve and validate the handoff.** Read repository conventions, the parent specification and revision, the complete native child tree, blockers, acceptance criteria, planning baseline, integration branch, original target branch, and per-ticket implementation and pull-request branches. Follow pagination and include nested, open, and closed children. Require an explicit, reachable planning baseline and every required ticket to be implementation-ready or already delivered with verifiable evidence. Reject an integration branch named `main`, equal to the repository's default branch, or equal to the original target. Surface missing or conflicting specification, relationship, or branch metadata instead of inventing it.
4. **Create or resume delivery state.** Resolve the absolute Git common directory and keep the orchestration run under `<git-common-dir>/parent-deliveries/<parent-key>/<run-id>/run.md`. Record the freshness audit with target SHA and source revisions, canonical issue identities, the ticket and blocker graph, branch tips, child run paths, PRs, reviewed SHAs, merge gates and results, the finalization run, and the current phase. Reuse existing ticket and finalization runs. On resume, repeat the freshness gate when the target tip, specification, or issue tree changed; otherwise verify the recorded inputs and continue the incomplete step without repeating implementation or merge operations.
5. **Choose the next ticket.** Process required tickets in a deterministic topological order. First classify existing delivery by verifying reviewed commits and merge evidence on the remote integration branch; issue closure or a PR label alone is insufficient. Skip a ticket only after recording that evidence. A remaining ticket is ready only when all required blockers are verified in the integration branch or explicitly excluded by the authoritative specification. Re-read the issue tree before starting each ticket so newly recorded decisions and dependencies are honored. Do not start finalization while any required ticket is undelivered, blocked, or awaiting a human decision.
6. **Implement the ticket.** Invoke `$implement-ticket` with the ticket and parent handoff. Let it run its complete review/fix loop and publish the exact cleared candidate. A child ticket must use its declared ticket branch and target the exact integration branch. When the planning handoff intentionally assigns a single ticket directly to the integration branch, require its cleared commit to be the verified remote integration tip and skip the child-PR merge step; its target draft remains unmerged.
7. **Gate a child merge.** Immediately before merging, fetch and verify all of the following against fresh provider and Git state:
   - `$implement-ticket` completed with a clean review for the exact remote head and current specification, passing candidate checks, no unresolved finding, decision, blocker, or exhausted correction loop, and a complete native ticket association.
   - The pull request is open, unmerged, based on the exact integration branch, and its head equals the reviewed and published candidate. The integration branch still contains the planning baseline and every delivered blocker. Unexpected base movement is reconciled through the existing ticket run and renewed review whenever it changes the reviewed diff.
   - Required provider checks and repository merge requirements pass for the current head and base. The pull request is conflict-free and contains no unrelated commits. Never waive, dismiss, or bypass a required check or approval.
8. **Merge only into integration.** Mark the cleared child pull request ready if required, then use a repository-supported merge method that preserves the reviewed commits; never squash, rebase, force-push, or rewrite the reviewed history. Do not enable a merge that could target a different base. Read back the merged PR, fetch the integration branch, and require the provider's merge commit and every reviewed ticket commit to be reachable from its remote tip. Record the exact merge evidence before selecting another ticket. A failed or ambiguous merge leaves the run pending; do not recreate the PR or substitute a direct push.
9. **Finalize the parent.** After every required ticket is verified in the integration branch, refresh the full tree and invoke `$finalize-parent` with the parent and orchestration run. Let it perform cleanup selection, integrated end-to-end verification, the HTML delivery report, final independent review, and publication of the integration draft PR to the declared original target.
10. **Verify the handoff.** Require `$finalize-parent` to finish with the reviewed integration head, passing required checks, correct target, and verified parent and child associations. Confirm the integration pull request remains open and draft. Report the freshness audit and target SHA, delivered and excluded tickets, child PRs and merge commits, integration head, final draft PR, checks, HTML report, review counts, decisions, and both local run paths.

## Stop conditions

Preserve state and stop when the issue tree is not fully specified, no ticket is ready because of an unresolved dependency, a child workflow reports `needs-human`, `blocked`, or `limit-reached`, a merge gate fails, or finalization is incomplete. Continue other independent ready tickets only when doing so cannot invalidate the blocked ticket's base or accepted specification.

Never close issues directly, merge the final integration pull request, mark it ready, retarget it, or merge anything into `main` or the default branch. The user owns the final merge.
