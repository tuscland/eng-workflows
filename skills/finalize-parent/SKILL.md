# Finalize Parent

```text
/finalize-parent <parent-issue-or-local-run>
```

The calling agent authors cleanup and coordinates final delivery. This workflow explicitly requests review subagents. Read the [local loop contract](../implement-ticket/references/local-review-loop.md) for upstream composition, persisted state, correction counting, native issue association, and the PR review record. This skill supplies the parent-specific inputs and publication sequence below; do not invoke `implement-ticket` to finalize each child again.

Invocation authorizes opening or updating the integration draft PR, implementing well-supported cleanup within the delivered parent scope, end-to-end testing in the repository's isolated test environment, creating the HTML delivery report, local commits, and publishing the independently reviewed result. Ask for human guidance on consequential scope, behavior, compatibility, or architecture choices. Continue independent work while awaiting that guidance. Never merge PRs, close issues directly, mark the PR ready for review, or file cleanup tickets without separate authorization.

## Workflow

1. **Resolve the delivery and resume state.** Read repository conventions, the parent's authoritative specification, native child tree, and planning handoff. Resolve the canonical parent, integration branch, original target branch, planning baseline, and artifacts. Fetch both branches. Reuse the integration branch's existing author worktree and any `parent-finalization` run; if no worktree exists, create one under `.worktrees/` for that branch. Preserve uncommitted work and reconcile unexpected local/remote changes before editing. Missing or ambiguous branch handoffs require resolution, not an assumed `main` base.
2. **Verify child delivery.** Enumerate all children, including nested children and closed issues, with pagination. Read every associated child PR's current body, review record, relevant review discussion, changed files, merge state, and base. Match by canonical repository and issue identity, using native relationships and explicit handoffs rather than titles or branch names. Verify that each required child's delivered changes are present in the integration candidate: check its recorded merge/squash commit and resulting code, not merely whether the original feature head is an ancestor. An open child issue can already be delivered because automatic closure is deferred. Record superseded PRs and explicitly approved exclusions. Unmerged required work, missing acceptance criteria, reverted delivery, or unresolved child decisions prevent completion; do not silently merge, cherry-pick, or drop children.
3. **Open or reuse the integration draft PR.** Once the delivered scope is established, use the existing pushed integration head to create the draft against the declared target, or reuse the exact existing head/base PR. Do not push unreviewed cleanup to open it. Start with the parent outcome, included child PRs, and a clear note that cleanup assessment and final review are pending. Record the PR URL immediately. An existing non-draft or merged PR requires reconciling the delivery state before changing it; do not create a duplicate. Keep the draft open if later work is blocked.
4. **Select cleanup.** Follow [Cleanup selection](references/cleanup-selection.md). Re-read opportunities in every child PR, deduplicate overlapping proposals, and verify them against the combined integration code. Rank by impact, cost, confidence, and risk. Record a disposition for each: execute, needs human guidance, defer, already resolved, or unsupported. Select the most promising bounded work; do not stop at producing a recommendations list. If no candidate merits execution, record why and continue to final verification and review.
5. **Execute and verify.** Run `/implement` for selected cleanup under the shared composition contract: implementation, meaningful tests, verification, and local commits; the final independent loop supplies review. Preserve parent and child acceptance criteria. Record actual changes and checks against the resulting candidate, and update opportunity dispositions. Run repository-required checks and integration tests that exercise interactions between children. Avoid empty commits when no change is needed.
6. **Test end to end and produce the HTML report.** Follow [End-to-end testing and delivery report](references/delivery-report.md). Run the required user/consumer journeys on the integrated candidate, including interactions between children and meaningful failure paths. Capture actual demonstrations and test evidence, then create a self-contained HTML report explaining the resulting behavior, code changes, cleanup, and verification. This step is required even when no cleanup was selected. Failed or blocked required scenarios, missing demonstrations, or an absent report prevent completion; unit tests and child PR checks alone do not satisfy it.
7. **Run the final review loop.** Follow **Parent review scope** below. Review the entire integration change against the target, including planning documents, all delivered child changes, cleanup, end-to-end evidence, and the HTML report. On findings, the same author verifies each finding, fixes supported defects through `/implement` or rebuts with evidence, writes the response, and returns to independent review. Refresh end-to-end runs, demonstrations, and the report for each changed candidate before review. Apply the shared limit of three correction cycles after review 0, including review after correction 3. Only the reviewer closes findings. Unresolved decisions, failed verification, or `limit-reached` preserve the draft and local run without publishing new commits or claiming finalization.
8. **Publish the reviewed result.** Apply the shared publication conditions to the exact parent candidate and specification, with passing end-to-end evidence and a reviewed HTML report for that candidate. Re-fetch and reconcile the integration and target branches; renew verification/review if their movement changes the reviewed diff or invalidates test evidence. Normally push only the reviewed commit history, then update the existing draft PR with the complete delivery summary, validation, cleanup dispositions, remaining debt, report summary/link as described in the report reference, and final review record. Add closing directives and verify native associations for the parent and every delivered child whose acceptance criteria are satisfied, including nested children. Use the shared `addCloseIssueReferences` procedure for missing links; paginate relationship reads and compare canonical IDs. Do not link deferred, cancelled, or unrelated tickets for closure. If the target is not the default branch, explicitly report deferred automatic closure.
9. **Report completion.** Verify the remote head, target, body, issue associations, and required PR checks for the published SHA. Pending or failing required checks leave finalization incomplete; preserve the draft and resume that verification. Code fixes for failing PR checks return through the same correction budget, end-to-end verification, report refresh, and independent review before another push. Add the final review/CI status to the HTML report without changing its reviewed behavior or code explanation. Report the clickable HTML artifact, draft PR, delivered children, executed cleanup, deferred opportunities ranked by impact/cost, human decisions, local checks and PR checks, correction/review counts, commit, and local run path. Retain the worktree, report, evidence, and run. Finalized means the reviewed delivery is ready for the user's merge decision; this workflow does not itself merge or close issues.

## Parent review scope

Use the shared local run layout with workflow kind `parent-finalization` so the parent implementation run and its correction budget are not reused accidentally. Persist the parent/child specification snapshot, child and PR inventory with source revisions and delivery evidence, cleanup decisions, initial remote integration head, target tip, planning baseline, candidate SHA, PR URL, checks, end-to-end scenario/results manifest, demonstration evidence paths, HTML report path/version, review reports, and publication phase. Keep this coordination state outside tracked files. An interruption resumes this run and its budget rather than starting over; evidence from a different candidate is retained as history, not reused as final verification.

The integration branch is both the implementation branch and the implementation base for the shared publication checks: confirm it retains the planning baseline and required artifacts. Pin the review base to the merge base of the fetched target and the integration candidate; record the fetched target tip separately. The planning baseline is required delivery evidence, **not** the final review base: reviewing only changes since it would omit some of the parent's work. Give the reviewer the parent specification plus all required child acceptance criteria and accepted cleanup scope, with their source revisions. A changed specification or reviewed diff invalidates earlier clearance; preserve superseded reports without resetting correction attempts.

Finish initial cleanup selection and implementation before review 0. After that first review, newly selected cleanup or author code fixes reserve the next correction attempt before authoring and return to independent review, even if the previous review was clean. External branch movement alone invalidates clearance without consuming a correction, but does not authorize extra author fixes outside the budget. After three attempts, defer additional optional cleanup or obtain explicit authorization for a new budget; required defects still prevent completion.

Spawn a reviewer without author conversation history using the [reviewer instructions](../implement-ticket/references/review.md), run path, pinned review base, candidate, specification snapshot, child inventory, end-to-end results and demonstration evidence, HTML report, and prior reports/responses. It runs `/code-review`'s independent Standards and Spec agents over the full parent diff, including interactions between children and accepted cleanup. Require it to check acceptance-criteria coverage, candidate identity, observed results, and the accuracy of the report's demonstration and code explanation; record the HTML version inspected. Missing, stale, or unsupported evidence cannot receive a clean outcome. Child PR approvals do not substitute for this pass. Wait for the complete report and its subagents before editing. If delegation is unavailable, preserve the run and report that blocker instead of substituting author self-review.

The initial draft contains only already-published integration history. Keep newly authored cleanup and corrections local until final review and checks pass. On partial publication, verify the remote head and resume only missing push, PR-update, association, or check-verification steps. Never rewrite reviewed history or force-push to reconcile a moving integration branch.
